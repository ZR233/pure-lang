# 14 - Thread Runtime 宿主与会话工具任务

本文定义 Studio 侧的 Thread 装配、激活、输入受理、步骤限制、后台工具任务交付与消息唤醒。
core 内核契约见 [16](./16-core-contracts.md)，状态与历史存储见 [15](./15-session-storage.md)。

## 14.1 统一装配与激活

Studio 的 Thread 工厂解析配置、Profile、Mode、项目和物理工作区绑定；Thread 装配器登记准备
owner 并创建 core Thread。root、child、冷恢复走同一装配入口。准备中的 owner 不对外发布；
失败或等待者取消不丢失释放责任——装配失败或调用方取消时仍由登记表保有已创建 owner，
关闭成功才删除登记。关闭先封闭装配，等待准备收束，再按子到父顺序关闭，失败保留重试入口。

激活先登记准备 owner，再创建物理服务与 core Thread；并发等待者共享准备结果，取消等待者
不丢失准备 owner，关闭会取消并等待仍在准备的任务。冷 child 从保存的
workspace/project 绑定创建新实例，不重新创建 worktree 或重演历史副作用；其父 Thread 必须
先激活。

每 Thread 独占模型会话与工具实例；同批声明和 executor 由 core 冻结。配置、Profile 与工作区
语义由 Studio 解释，不进入 core 类型；root 的无凭据模型 selector 作为不透明
`studio.model-route` 扩展进入当前 checkpoint，并由 effect 记录修订历史；child 使用冻结的 Profile
snapshot。服务可按隔离身份共享租约，关闭一个 Thread 不撤销
其他 Thread 的租约。模型切换由 owner 串行执行：关闭旧会话后清空旧 continuation 与重试计划，
再创建新会话；工厂失败时 Thread 明确保持模型不可用，保留历史并允许重新装配。执行中的
Turn 不被参数刷新中途替换，后台工具任务与模型切换互相独立。

路由 selector 与 pending model update 必须由同一 owner mailbox 操作提交：扩展 CAS 失败不改变
pending update，反之亦然；selector 表示 desired route，实际模型仍在下一 Turn 边界替换。
provider 设置更新可触发模型和工具刷新，但刷新必须逐 Thread 读取自身 selector 并重新解析，
不得广播某个全局角色路由。selector 已失效时 Thread 进入明确 unavailable 状态，不猜测 fallback。

## 14.2 输入受理与驱动

输入以调用方稳定 ID 幂等受理；Studio 的 submitPrompt 由 core 原子选择启动或打断后继续，
客户端不根据可能过期的活动状态选择命令。Core 的 Start/Steer/Queue 仍是独立的通用输入策略。
HTTP 使用 `POST /api/v1/threads/{thread_id}/prompts`（`prompt.submit`），FRB 使用 `submitPrompt`；
请求的 `input` 包含稳定 `inputId`、`text` 与 `attachmentDraftIds`。同 ID 重试必须保持原内容，
附件草稿在首次受理后即提交，因此重复请求先从 canonical 输入记录返回原回执，再决定是否需要准备资源。受理不伪造 Turn ID：产品提示词
提交返回 inputId 和该输入首次受理的 commit 序号，客户端通过同 ID 的输入时间线条目关联实际
Turn；Turn DTO 与 Turn 时间线条目保留实际 inputId 关联，即使模型准备失败也能把失败对应到
已受理输入，不复制一条从未交付模型的用户消息来伪造关联。受理和模型准入是不同提交：受理
即返回幂等回执，该回执跨窗口、跨重启稳定——稳定 `inputId` 的最小身份与产生它的 effect 同一
history 事务写入，重复提交先查该 durable 身份索引（见 [15](./15-session-storage.md) §15.3）；
只有模型准备完成、权限与容量复核通过后，消费状态才与实际请求记录及用户上下文同一提交。
准备失败保留输入，驱动暂停不自动产生新的收费尝试。

steer 记录原目标 Turn，在下一份模型请求冻结时按序加入用户上下文，并与该请求一同提交消费
事实；冻结后到达的 steer 留待后续请求。未消费的 steer 与其他输入一样保留，可在中断恢复后
继续处理，不改写已执行请求。附件在受理前保存并验证长度、摘要，完整业务元数据与实际模型
上下文一同进入 Thread；草稿只在输入受理后提交。

执行授权用互斥状态表达：Dormant、Enabled、Paused、Failed；普通消息只能唤醒 Dormant/Enabled，
显式继续才能解除 Paused/Failed。物理取消的目标 Turn 与授权正交，停止不会提前解除清理屏障。
当前输入批次只有一份身份集合，首条输入身份从集合派生；不额外维护平行的当前输入状态。

持续执行输入队列的驱动属于 Thread actor：Studio 显式启用驱动并传入通用步骤上限，之后
actor 串行处理已受理输入，产品层不为每个输入生成旁路执行任务。普通 owner 命令在下一轮
驱动前处理，模型与工具配置可在 Turn 边界生效。执行失败、交互暂停或步骤上限停止驱动，
避免自动重复有费用的请求；新输入的受理本身不解除暂停，宿主必须明确继续。驱动状态只描述
物理执行，不在冷恢复时自动激活。

root 与 child 使用同一 Thread 机制；Profile、workspace assignment、父子目录、spawn/close 及
消息路由由 Studio 协调，工具层只调用宿主端口，不拥有第二套子代理运行时。Profile 的
directory/worktree 边界由物理工具后端执行；shell/Git/MCP 的能力需单独授权。

提交并继续在同一 owner mailbox 操作中先受理内容，再绑定当前 Turn 代次并请求取消。受理失败不
打断原执行；重复 ID 不重新唤醒或取消。当前 Turn 的在途工具一并取消，尚未启动的调用收束为取消；
待执行和清理结果均提交后才可开始新模型请求，其他 Turn 的后台任务保持其原生命周期。
收束期间的输入按受理顺序合并到下一请求，每条输入保留自己的受理及消费事实。已消费内容不重放；
尚未准入模型的原输入与补充内容共同交付。取消中的状态属于活动 owner，不恢复物理取消令牌。
停止或关闭撤销自动继续意图；失败保留待处理输入并暂停，不自动重试收费请求。
迟到的普通通知只保留唤醒水位，不能解除显式停止或失败暂停；新的明确输入或显式继续才能恢复。普通消息通知不使用
这一控制入口，不能因 child 进度或后台结果到达而中断父 Thread。待决交互必须通过专用回答入口解决。

## 14.3 步骤限制、停止与取消

执行预算、步骤限制和取消属于通用类型化执行政策；Profile、角色和父子生命周期的决定属于
宿主。步骤策略明确区分 Unlimited 与 Limited：Studio 主会话的新建、恢复和所有续接均使用
Unlimited，不因累计模型调用次数或活动总时长停止；子会话每个 Turn 的上限为 256 步。
每个新 Turn 从零计数，获得完整额度，不继承前一 Turn 的消耗；同一 Turn 内的模型与工具往返
不刷新额度。达到上限后暂停，显式续接开启新 Turn 时重新计数。用户停止、关闭、
交互、真实错误与单次外部操作超时独立生效。旧 stepLimit 历史保持原样，不自动重启已经停止
的任务。不得通过产品 JSON 字段改变 core 控制行为。

带预期 Turn 身份的中断由 Thread mailbox 在 owner 内核对并取消同一执行代次；产品不得先读取
快照再取消一个可能已切换的 Turn。停止同时暂停输入驱动，不删除待处理输入，后续继续必须
显式恢复。Turn 取消时，已准入但尚未启动的工具调用以取消结果收束，不执行副作用；这些
结果与 Turn 取消终态同 commit 发布。Thread 关闭也先收束未启动调用，再关闭工具实例，避免
留下无法配对的结束历史。中断句柄只持有当前命令的子取消令牌，不共享可变 transcript 或任务
状态；中断在命令队列之外生效，不取消调用方复用的父 token，也不影响下一执行代次。

模型调用被运行时定向中断（插入消息、停止、关闭或重定向）取消时，模型实现必须把结果以取消
语义上报，不得归类为 provider 不可用或传输失败。宿主据此把该次 Turn 收束为取消终态并继续
消费已受理输入，而不是把定向中断记成失败并暂停驱动；真实 provider 故障、超时与传输错误保持
原语义。判定依据必须是调用自身的取消事实，不能仅凭错误文本或同一时刻的其他信号推断。

## 14.4 后台工具任务与交付

Thread owner 串行拥有任务、交付与消息状态。任务先提交 Running 事实再执行。普通工具默认
一秒交付窗口：窗口内完成提交实际结果，超时提交原调用关联的任务回执，执行 future 留在
Thread。后台完成将结果、任务终态与消息一次提交，模型在后续请求准入时消费；已受理任务可
跨 Turn 运行，终态不得重复交付。回执和最终业务结果是不同事实。

工具等待只报告就绪，完整后台结果由模型准入统一消费，避免 wait 与收件箱重复交付。任务查询
不消费消息；任务取消只提交意图并请求执行 token 取消，直到执行与物理清理返回才产生终态，
不把 Requested 当成完成；重复取消不重复提交，终态不可被取消命令改写，取消单个任务不取消
其父 Turn。任务查询/等待/取消只接收本 Thread 回执的完整 taskId，未知任务返回 TaskNotFound，
不猜测前缀或修改大小写，也不泄露其他 Thread 的任务。

完整业务 payload、观察结果、实际 delivered context 和任务终态分别保存。失败可携带已观察
输出；取消后迟到结果仍保留，但不应用其扩展、交互或结束控制。实际模型历史使用已保存的
delivered context，不能用当前渲染器重新解释旧业务正文。

执行完成而提交失败时，owner 保留原始完成对象与执行租约，暂停新模型准入；提交重试不再次
执行工具。完整载荷与上下文同日志保存，不按工具类型建表。大型二进制或输出文件使用带摘要
和长度的稳定资源引用；单页预览、临时路径或尚未归档的 capture 不等于完整资源。

`exec` 与 `write_stdin` 共享 Thread 私有进程管理器，任务身份校验先于内部进程映射。输出必须
排空后才归档，远程归档使用真实远程范围读取；失败保留源 capture，不重演命令。物理权限和
工作区限制由工具后端执行，core 不根据工具名或参数路径猜测授权。

Studio 统一装配 root/child/恢复的工具和物理服务，不在每轮重建命令管理器或保存另一份
registry。动态目录变更保持仍有效的物理租约；SSH 重连保持服务器、工作目录与权限边界，
替换失效连接的工具与命令管理器；同一连接的目录刷新继续复用命令管理器。候选工具成功交给
Thread 后才发布新绑定；失败、取消或目标失效不得记录为安装成功。旧连接任务保留中断结果，
不重放命令或把旧进程输入转交新连接；关闭逐个等待实例，失败保留进度重试。刷新按会话独立
推进，同一会话串行安装并合并重复通知；一个会话的连接或清理等待不阻塞其他会话。技能事实
通过 owner 消息通道受理，按来源保留最新待应用值，在下一次模型请求准备前应用；受理不修改
已冻结的模型输入，也不等待整个 Turn 结束；关闭拒绝新更新并收束在途刷新。

## 14.5 消息与统一唤醒

消息以稳定 ID 幂等受理，来源和上下文不能冒充 system 或审批。消费水位与模型请求准入同
commit，准备失败或准入前取消不消费。明确输入、后台消息与 UI 观察有各自语义，消息到达不
隐式创建有费用的模型尝试。模型和工具执行期间，Thread owner 仍受理消息及历史读取：消息
进入同一个 owner 的收件箱并提交，但不改变已冻结请求或当前上下文，只能在后续请求准入时
消费。该通道有界，不持有另一份 Thread 状态，也不能绕过关闭受理门禁。

宿主可显式要求消息唤醒 Thread：唤醒水位与消息受理一同提交；活动 Turn 若已消费该消息，
结束后不再额外调用模型；未消费消息在空闲时通过运行时上下文启动执行，不伪造用户输入；
冷恢复保留唤醒事实但仍需宿主明确恢复驱动。

## 14.6 生命周期与观测

启动只读取轻量 catalog，不遍历或激活会话。目标 Thread 激活时读取并校验其 checkpoint，缺失
checkpoint 或产品关联明确失败，不创建空会话掩盖数据丢失；实际服务在显式激活时装配。停止、
关闭与任务取消由 owner 核对执行代次：关闭先禁止新工作，取消在途执行并等待物理结束，重试未
提交结果，再关闭工具与模型，flush 该 Thread 的固定历史/调用水位并保存最终 checkpoint；关闭
失败保留 owner。冷恢复把遗留 Running 收束为 Interrupted，不恢复旧 executor 或自动重放副作用。

订阅使用当前状态 snapshot 与增量 effect；历史分页始终通过独立 HistoryReader，执行 owner 关闭后
仍可读取数据库中的最终事实。归档等待整棵
Thread 树关闭、保存成功与工作树清理收束（成功，或回落 `preserved` 并发布诊断）。SQLite
writer 的失败与未保存事实必须可观察；目录 writer 只保存
产品关联，不代理 Thread effect、历史或 checkpoint。

## 14.7 交互与业务状态的宿主侧

Studio 从通用 interaction/permission snapshot 投影产品问题，并按带 Thread 归属的不透明 ID
路由回答。Plan 和 workflow 由 Studio 解释，更新使用扩展 CAS；回答、扩展、实际上下文与
continuation 输入在同一 core commit 中提交。重复回答不重复入队或自动驱动。

Mode 切换使用 idle reconfigure：核对水位并拒绝活动 Turn/任务/输入/交互，原子替换业务扩展、
目标 Mode 默认模型 selector、下一 Turn pending model update、上下文及工具目录；旧历史正文不按当前 Mode 重新渲染。普通用户提问、Plan 确认和执行许可
共用 Studio 类型化交互路由：路由从 core snapshot 读取事实，不建立另一套可写交互状态；
用户回答作为一次原子响应与隐藏续接输入提交，模型只接收保存时确定的内容。对外交互 ID
包含 Thread 与 core 本地交互身份的无歧义编码，客户端只透传不透明 ID，provider 在不同
Thread 中重用调用 ID 不会造成回答串路。
