# 工具的 Thread 边界

具体工具只实现 `pl_core::tool::opaque::Tool`，以 `Registration` 将实例所有权交给 Thread。参数 schema、业务权限分类、JSON 解析、工作区约束和输出投影属于 pl-tool；core 不保留 StaticTool、ToolCallContext、SessionRuntime 或产品 working set 的适配入口。

文件、命令、Git、LSP、MCP、Skill、搜索和交互工具共享现有领域后端。工具输出分别保留完整 payload 与模型可见 context；已观察到副作用的失败通过 `ToolError::with_output` 保存事实。Note、Todo 和 Skill 激活使用 Thread 扩展，工具不持有第二份会话状态。

工具测试通过动态接口或纯领域后端验证行为；旧静态注册框架的重复装配测试随旧入口移除，其生命周期、权限、输出和重放风险由 Thread 契约测试负责。

Programmatic 调用资格由具体工具的声明提供：LSP、只读 Git、已解析为只读的 MCP 工具和 MCP 资源查询携带允许调用方及输出 schema。未知效果、写操作、交互和状态更新不自动获得资格；模型适配只按已验证的 route/hosted capability 决定是否编码这些已声明资格，不按名字推断权限。

命令进度通过 `TaskAccess` 上报有界的通用内容预览。预览只属于原任务、原执行器和仍在运行的 Thread，更新不提升 journal 水位、不进入模型 context 或冷存储。Thread 终态提交清除预览；历史重放只采用已提交完整结果。命令采集端合并至 64 KiB 预览并标记截断，完整输出仍由归档服务保留；预览传输与命令执行同生命周期，不派生无 owner 的后台队列。

热目录刷新订阅产品配置、MCP generation、Skill 目录以及语言服务目录事件。刷新只重新构造具体工具声明与执行器，不重放历史、不重读指令、不刷新 SQLite；核心注册表原子替换后，旧模型 step 的执行器继续持有原租约，已撤销权限按新目录拒绝后续准入。一个 Thread 的命令管理器跨目录刷新复用，缓存只持弱引用；同 ID 的新 owner 不继承旧 owner 的物理资源。已冻结的 workspace/SSH 目标发生变化时清空不可再授权的目录并报告必须重新激活，不能偷偷改为访问新路径。

SSH 配置或凭据变更单独通知目录刷新并撤销旧物理绑定；日志和信号不携带 secret。目录刷新失败关闭可调用目录并发布恢复问题，下一次相关配置/目录变更重新尝试；物理目标变化必须显式重新激活。关闭观察 barrier 成功后回收绑定缓存，失败时保留以便重试。

成功加载主 Skill 文档的历史工具结果通过生产者的版本化 codec 投影为独立 Skill 时间线项；排序位置在结果提交时固定预留，重复目录刷新不重写激活事实。未知/损坏结果只保留原始工具记录，不伪造激活；辅助资源读取不产生主技能激活项。

目录重连复用同一 Thread 的执行策略租约；仅权限模式或自动审核模型绑定的实际配置变化才生成新策略身份。服务 generation 或 Skill 目录更新本身不撤销已冻结调用，真正的权限变化仍由 core 在执行准入时拒绝旧调用。

创建时的 Skill 目录进入稳定指令前缀；之后目录变化通过 `studio.skills` 独立 runtime fact 追加，首次相同目录和重复内容不追加。待执行工具批次期间暂缓事实更新，继续使用当次已冻结目录。新用户输入按当时目录、查询与已加载技能名生成建议，并与该输入一起冻结；恢复或重试不重新计算建议。

Provider/core 调用 ID 进入命令进程与归档边界时，转换为有界 `task-` 加 SHA-256 的物理身份，不能直接作文件名。`exec` 与 `write_stdin` 使用同一映射，目录重建继续引用同一 Thread 的进程管理器；不同 Thread 的管理器保持隔离。

过期工具候选的关闭失败由 Studio 持有原始可重试资源及拒绝原因，并绑定原 Thread incarnation；失败候选清理完成前不再次构造同 owner 的候选，不把失败指纹标记为已安装。目录 watcher 采用协作停止，完成在途资源移交后再退出；shutdown 重试未完成候选关闭，失败返回错误并保留 owner，取消 shutdown 等待也不得丢失资源。

协作查询（包括 `list_agents`）只读取宿主授权范围内的快照，允许与普通读取工具出现在同一模型批次；该批次不承诺跨工具的联合事务快照。创建、发送消息、打断和关闭代理会改变协调状态，仍必须单独调用，不能与查询或其他工具混批。

注册的执行等待策略与模型批次约束分开：`foreground()` 保留必须单独调用的既有语义；
`foreground_coexisting()` 表示可同批的前台工具，按模型调用顺序等待终态且继承本轮取消。
真正控制权限始终要求 Solo，不可通过可同批前台能力降级；普通后台任务仍保留一秒后返回运行回执。
`write_file`、`apply_patch` 和 `write_stdin` 使用可同批前台能力；现有 writer 互斥保持，
不新增跨后台或外部进程的读写事务保证。`write_stdin` 只等待写入完成，不等待 exec 进程终态。
