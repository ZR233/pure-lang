# Rust 模块与依赖

## 1. crate 边界

按领域所有权、复用边界和运行时依赖划分 crate。新增 crate 必须有真实调用方、独立不变量和清楚依赖方向；只为规避循环依赖、隐藏转发函数或预留未来扩展而新增 crate，通常说明边界尚未找准。

遵守项目既有职责：跨 crate 公共协议属于 `pl-protocol`，provider 适配与流归一化属于 `pl-model`，核心 turn/session/store/tool 编排属于 `pl-core`。新增概念前先判断真正所有者，不把产品、GUI、存储或第三方 adapter 细节推入核心领域。

## 2. 模块与可见性

模块默认私有。稳定领域边界优先使用 `pub mod` 形成表达所有权的可读命名空间；只有少量高频入口确实属于上层 facade 时才使用精确 `pub use`。上层 crate 不应为方便而代理重导出专项 crate 的整套 API，除非它明确拥有该 facade 契约。

只有当某个模块的全部公共项都属于上层稳定 API 时，才使用 `pub use module::*`；不得通配暴露 `raw`、`imp`、`sys`、`unsafe_impl` 或第三方底层细节。同一接口只保留一条 canonical 公共路径，不同时保留根路径与子模块路径。

单一职责且不拥有子模块时使用 `foo.rs`。模块已经拥有多个真实、内聚的子职责时才使用 `foo/mod.rs` + `foo/child.rs`；禁止只有 `mod.rs` 的目录和只转发唯一子文件的目录。`lib.rs` 与确有子模块的 `mod.rs` 作为目录页，只说明职责、声明模块和导出稳定入口；大量实现下沉到职责明确的子文件。

公共路径变更时先列出 crate 内、workspace 内和仓库外兼容责任。在同一改动中迁移可控调用方，并搜索旧路径、旧重导出和文档示例；没有明确跨版本责任时删除兼容别名与代理层。测试遵守生产可见性，不为方便测试扩大公共接口或增加只供测试穿透内部状态的入口。

## 3. feature 与条件编译

把 `cfg` 放在真实平台、可选后端或宿主边界。公共入口在支持组合中保持一致，不让调用方到处重复条件编译。未启用能力时返回明确不支持，或在编译期移除整个能力；不保留静默成功的空实现。

让 feature 单调、可组合，并避免暗中改变同一接口的所有权或错误语义。默认门禁不启用 `live-tests` 等外部服务 feature；新增组合按项目规定选择静态检查或显式 opt-in 验证。

## 4. 依赖管理

优先使用 `[workspace.dependencies]` 与 workspace crate 名称。新增依赖前评估必要性、维护状态、license、公共 API 泄漏、编译时间、体积、安全成本和现有替代方案。

避免临时 Git、绝对路径、仓库外路径和非预期 registry 覆盖。升级或切换依赖时检查 feature 变化、重复版本造成的类型割裂、目标平台支持和许可证边界。低层领域 crate 不依赖高层产品编排；共享抽象由能力所有者定义，不创建无领域语义的公共杂物 crate。

## 5. 宏与诊断

宏只用于语言的函数、泛型、trait 和 derive 无法清楚消除的重复，不隐藏复杂控制流、资源所有权或错误传播。导出宏使用 `$crate` 定位自身 crate，选择准确 fragment，并让展开错误指向调用点或明确契约。

公共类型在不泄漏敏感或无界内容的前提下提供有意义的 `Debug`。诊断保留阶段、对象和原始状态，但不要让面向人的格式成为隐式机器协议；机器输出应使用明确的 typed DTO 与 serde。
