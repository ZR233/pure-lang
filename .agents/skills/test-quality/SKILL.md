# 测试质量与必要性

测试的目标不是增加数量或覆盖率，而是以合理成本对重要错误提供可信反馈。先说明要防止的具体错误，再选择能够稳定暴露该错误的最小充分测试边界。

## 工作流

1. 读取根目录 `AGENTS.md`，确认受影响的 Rust、Flutter、生成文件、GUI 或 live provider 验证入口。
2. 重构或删测前先运行受影响测试并记录基线，再为每项保留或新增测试说明风险、层级、环境、判定、失败证明以及与现有测试的关系。
3. 新增或修改测试前执行必要性门禁；审计现有测试时给出 `保留`、`重写`、`下移`、`移出门禁` 或 `删除` 结论，并指出被删风险由哪里继续保护。
4. 涉及并发与取消时叠加 `rust-concurrency-safety`；涉及 unsafe、FFI 或 FRB 边界时叠加 `rust-unsafe-safety`；普通 Rust 实现遵守 `rust-code-quality`。
5. 只有用户要求解释方法论、引用书籍或论文，或质疑删测依据时，才完整阅读 [方法论依据](references/evidence.md)。

## 1. 同时描述目标与执行条件

不要只用“单元测试”或“集成测试”描述用例。先说明想证明的风险，再记录实际环境；层级不由框架、目录或进程数单独决定。

| 层级 | 主要责任 | 默认不负责证明 |
| --- | --- | --- |
| 单元或组件测试 | 一个可独立理解组件的规则、边界、状态转换和错误处理 | 真实进程、文件系统、网络、GUI 或跨语言装配 |
| 组件集成测试 | 同一应用内多个真实组件的接口、装配和协作 | 完整用户旅程与真实平台边界 |
| 契约测试 | Rust crate、provider、wire、FRB 与 Dart 双方对请求、事件、错误和版本语义的共同理解 | 提供方完整副作用和 GUI 交互 |
| 系统集成测试 | 本系统与文件系统、进程、网络、模型 provider、原生 bridge 或浏览器的真实边界 | 穷举局部业务规则 |
| GUI/端到端测试 | 完整装配与少数关键用户任务、布局和交互 | 大量输入组合与细粒度故障定位 |

单元不等于一个函数，也不要求替换所有协作者。多个真实组件在同一进程内协作可以是组件集成。验收测试描述“证明用户需求”的目标，与物理运行层级正交。

层级确定后，记录进程/线程模型、真实实现或 fake/stub/mock、文件系统/网络/浏览器/GUI 使用、环境所有权、清理责任、预期耗时、门禁阶段和失败责任边界。在能真实暴露缺陷的前提下，选择反馈最快、环境最稳定、失败最易定位的层级。

## 2. 必要性门禁

每项测试回答五个问题；无法回答时先补需求、调用链或失败模型，不直接堆用例。

1. **独立风险**：保护哪个用户行为、公共契约、历史缺陷、边界条件、失败路径或运行时不变量？
2. **缺陷敏感度**：删除逻辑、反转条件、破坏返回值或恢复错误实现时，测试是否失败？
3. **独特信号**：现有测试是否已用同等或更低成本证明同一风险？
4. **最小充分层级**：更小测试能否保持真实性；更大环境是否确实增加装配、协议、时序、跨语言或平台证据？
5. **长期收益**：运行、诊断与维护成本是否与风险严重度、发生概率、历史频率和变更频率相称？

代码行数与复杂度只能作为风险线索，不能替代契约与故障分析。高损失、易发生、曾回归、频繁修改或跨所有权边界的行为优先测试。

### 2.1 以关键节点组织测试

关键节点是多个实现步骤汇合后首次形成稳定、可观察语义的边界，例如公共 API/跨组件装配、领域不变量或状态转换、typed 错误映射、协议转换、资源发布与关闭。优先用少量节点测试覆盖完整对象和最终后置条件，再在真正拥有复杂不变量的局部模块保留精确单元测试。

目录或模块重构后按不变量所有者重新安置测试，不按旧文件逐一复制。薄转发、简单构造、私有 helper、中间快照和 serde/第三方库已经保证的机械行为默认由上层节点自然覆盖；只有字段 rename/tag/default、适配规则或 wire 兼容本身是项目合同，才保留直接契约测试。不得为保留旧测试新增生产可见性、测试专用 getter 或兼容入口。

删测前把每个用例映射到独立风险和替代证据；同一规则的多个排列可以合并为表驱动或一个完整场景。测试数量下降不是目标，重要风险仍被更稳定、更接近公开语义的测试保护才是完成条件。

## 3. 让测试能识别错误

测试必须包含区分正确与错误实现的判定。只执行代码、只证明没有崩溃、只匹配成功日志或只提高覆盖率，不能证明功能正确，除非职责明确是启动探针。

- 断言完整可观察对象、结构化错误、状态变化、持久化结果或必要协议交互；Rust 断言优先按项目约定使用 `pretty_assertions::assert_eq!` 比较完整对象。
- 覆盖成功、关键边界和有实际后果的失败；状态机覆盖可达转换与重要非法转换。
- 修复缺陷时先让同一回归在错误实现上确定失败，再验证修复后通过；保留失败原因与可观察证据。
- 新行为可通过实现前失败、临时恢复旧实现、变异测试或故障注入补充检查缺陷敏感度，但不替代真实回归。
- 确保内部失败传播到最外层运行器；不能打印错误后仍以成功退出。

## 4. 保持稳定与可诊断

相同代码、输入和受控环境应得到相同结果。测试失败时要能区分产品错误、测试错误和环境错误。

- 测试自行建立并清理状态，不依赖执行顺序或其他用例残留。
- 控制时间、随机数、标识符、端口和资源分配；等待事件或条件，不用任意 `sleep` 代替同步。
- 不在测试中修改进程环境变量；确需修改时按项目规则隔离并恢复。
- 不占用保留端口 `1420`，临时服务使用动态端口并可靠回收进程树。
- 名称表达场景与期望，输入、动作和断言保持完整、简洁并靠近。
- flaky 隔离只能作为限期止损，必须有负责人和根因修复；不得靠无限重跑维持绿色。

随机、性能、压力、混沌与 live provider 测试可以使用统计判定，但应与确定性提交门禁分开，并明确样本、阈值、误报处理和失败解释。

## 5. 审计低价值测试

不必要测试不是“长期没有失败”，而是没有独特风险信号，或信号不值得持续成本。下列形态默认删除或重写；保留例外时必须指出可观察契约、能使测试失败的错误实现，以及低成本测试不能提供的证据。

| 测试形态 | 默认处置 | 合理例外 |
| --- | --- | --- |
| 只断言私有字段、helper 或内部调用顺序 | 从公开边界验证；无外部价值则删除 | 调用顺序本身是事务、协议或安全契约 |
| 为每个生产方法机械建立对应测试 | 按行为、边界和状态转换重组 | 独立公共函数本身就是完整契约 |
| 高层复述低层相同输入、行为和判定 | 删除高成本重复项或下移 | 高层增加真实装配、跨语言、资源或时序证据 |
| 复述标准库、框架或第三方行为 | 改测本项目配置、adapter 与错误映射 | 项目承诺特定版本包装契约 |
| 无断言、恒真断言或只为覆盖率触达 | 补有效判定；无目标风险则删除 | 明确标注的启动或存活探针 |
| 只验证 mock 调用次数而不执行真实逻辑 | 改用真实轻量实现或 fake，并补集成证据 | 故障注入或交互本身就是契约 |
| 替换全部协作者后声称证明完整功能 | 重新划定组件边界或上移真实集成 | 严格隔离算法或错误传播边界 |
| 巨大、不可审阅或盲目更新的快照 | 拆分并显式断言关键语义 | 稳定、短小、确定且逐项审查的输出契约 |
| 依赖任意 sleep、生产网络或共享状态 | 改为条件同步与隔离环境；否则移出门禁 | 独立生产探测，不冒充提交回归 |
| 长期 flaky 且失败只靠重跑消失 | 限期修复；无诊断价值则删除 | 独立统计测试使用专用判定 |
| 功能、调用者或兼容责任已消失 | 确认所有权后删除 | 旧数据迁移或长期支持仍受承诺 |
| 无逻辑 getter、setter 或纯转发测试 | 删除或由调用者行为自然覆盖 | 存在权限、转换、缓存等契约 |
| 自动生成但无人能解释风险与判定 | 人工筛选和重写，其余删除 | 生成结果已人工确认独特风险 |

沉没成本不是保留理由。删除前核对公共消费者、历史缺陷、兼容版本和发布门禁，避免误删低频高损失保护。

## 6. 跨层去重

代码覆盖重叠不等于测试重复。只有同时满足以下条件才按重复处理：

- 输入、行为和判定实质相同；
- 能发现的故障种类相同；
- 更高层没有增加真实装配、契约、并发、跨语言、GUI 或部署证据；
- 删除后不损失更快定位、外部兼容保证或独立所有权门禁。

优先保留最低成本的充分证明。GUI、浏览器和 Driver 层只保留组件层无法证明的布局、连通性、平台装配与关键用户任务，不穷举局部输入组合。`cargo xtask verify-gui --web-integration` 证明纯 Dart Web 布局与交互，不替代原生 bridge、文件系统、进程、MCP/LSP 或真实 provider 验收。

## 7. 交付

不得为了通过门禁而削弱断言、扩大成功匹配、删除确定性回归、增加无限重试或把真实失败改成跳过。使用 `AGENTS.md` 指定的 Rust、Flutter、GUI、生成文件与 opt-in live 测试入口，并在总结中列出实际运行项、结果及未运行原因。
