# 锁与生命周期

## 1. 选择同步方式

先判断是否能通过所有权转移、消息、不可变快照或任务内局部状态消除共享。确需共享时，让每把锁保护明确不变量，并记录锁内必须一致的字段与对外发布点。

临界区保持狭窄，但不要为了缩短持锁时间而发布不完整状态。不得持锁执行文件或网络 I/O、`.await`、复杂计算、进程等待、provider/tool 调用或未知回调。若无法避免，证明调用链不会反向取得当前锁，也不会观察半提交状态。

## 2. 加锁顺序与回调

存在多把锁时建立稳定顺序，并沿完整调用链检查嵌套取得；析构、错误格式化、日志和回调也可能间接取锁。需要同时修改多个对象时，按稳定键排序取得，或引入拥有真实事务语义的上层边界。

通知、listener 与完成回调通常先在锁内提取待通知对象或形成持有所有权的快照，再在锁外调用。快照必须保证资源仍存活。重复通知应幂等，或由代次/状态明确拒绝。

## 3. 等待与唤醒

等待必须在检查条件与进入休眠之间避免丢失唤醒。等待者在保护条件的同步边界内检查状态并登记，再释放锁等待；唤醒方先发布状态，再使等待者可运行。

唤醒不是状态。等待者恢复后重新检查条件，以处理虚假唤醒、多个消费者和状态再次变化。完成、超时、取消与关闭竞争时，明确哪个结果获胜、其他路径如何观察、谁负责移除等待者。

不要用任意 `sleep` 表达同步。测试使用 channel、barrier、notify、阶段 hook 或可观察条件，使错误交错可重复。

## 4. 资源生命周期

任务、连接、stream、临时文件、锁文件、Driver/DTD/GUI 子进程和 FFI handle 都要有单一释放责任。明确创建、发布、使用、取消、关闭、等待和回收状态。

部分初始化失败、登记后启动失败、处理中取消、调用方提前退出和关闭时仍有在途工作都要回滚。资源发布给另一执行上下文后，原 guard 不能再私自释放；取回责任需要唯一完成令牌或明确状态转换。

引用计数只证明内存仍在，不证明业务状态有效。关闭时先阻止新工作，再通知或取消在途操作，等待其结束，最后释放底层资源；陈旧句柄返回明确错误。

## 5. 验证

优先使用可控 barrier、阶段 hook、模型化状态机或顺序断言构造关键交错。验证最终状态、资源计数、错误传播和所有等待者，而不只验证“没有超时”。真实进程树或 GUI 生命周期语义必须使用项目规定的 integration/Driver 入口取得证据。
