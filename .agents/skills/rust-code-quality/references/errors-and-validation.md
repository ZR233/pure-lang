# Rust 错误与验证

## 1. 错误服务调用方决策

可恢复失败返回具有明确语义的 `Result` 或 `Option`，保留转换、重试、回滚与报告所需信息。不要用 `String`、`()`、panic 或日志代替业务错误。

公共错误遵循[类型与接口](../../rust-api-design/references/types-and-interfaces.md)：可以定义领域错误，也可以有意采用并精确重导出合适的第三方错误，不为改变来源增加无意义包装。非平凡自有错误优先使用工作区 `thiserror`；仅有明确依赖成本约束时手工实现。顶层命令和编排可沿用 `anyhow::Result`、`Context`、`anyhow!`、`bail!`，不把 `anyhow::Error` 泄漏到稳定库契约。

外部输入、资源耗尽、并发竞争或用户请求造成的失败必须明确传播；不猜测默认配置或后备路径，不伪造成功。`unwrap`、`expect` 和 panic 只用于测试或有证明的不可恢复内部不变量；一次性初始化也不能以此掩盖可报告的环境错误。`debug_assert!` 不承担发布正确性或安全校验。

## 2. 诊断与失败传播

说明失败的操作、对象和必要阶段，保留结构化原因；面向用户的边界只补充新的决策上下文，避免多层重复同一根因。不要输出凭据、用户内容或无界数据；轮询和重试诊断必须有界。

运行器必须让内部失败传播到最外层退出状态。零退出码、文件存在或成功日志本身不是完整功能证明；必须核对实际目标行为及后置条件。

## 3. 验证方式

测试必要性、布局与回归统一由 [test-quality](../../test-quality/SKILL.md) 维护。优先复用或增强完整行为测试，缺少独立证明才新增；同一回归在错误实现上稳定失败、修复后通过。不要靠概率复现、延长超时或放宽断言取得绿色。

运行器验证发现、选择、执行和失败传播；并发验证可控交错与最终进展；跨进程或跨语言边界观察真实行为及回收。只有被测对象就是源码文本、生成模板或静态契约时，才用文本作为主要判定，不能用文本匹配代替生产逻辑执行。

重构前建立受影响行为基线，过程中在可编译节点验证；迁移后检查旧入口、别名、重复解析和无消费者辅助代码。验证命令与提交前门禁只引用[项目约束](../../../../AGENTS.md)，不在技能重复维护。实际失败保留原始诊断，适用检查通过后按项目完成条件交付。
