# Rust 错误与验证

## 1. 错误边界

让错误类型服务调用方决策。可恢复失败返回具体 `Result<T, E>` 或具有明确语义的 `Option<T>`，保留足以转换、重试、回滚或报告的结构化信息；不得用 `String`、`()`、panic 或日志表达业务失败。

可复用 crate 使用自己的类型化错误，并在 adapter、repository、runtime 等边界转换第三方错误。命令入口和顶层编排可以沿用项目已有的 `anyhow::Result` 与 `Context`，但不要把 `anyhow::Error` 泄漏到稳定库接口。

`unwrap`、`expect` 和 `panic` 只用于测试或经过证明的不可恢复内部不变量。外部输入、资源耗尽、并发竞争和用户请求导致的失败必须传播。断言证明程序内部不变量，不校验不可信输入；发布正确性不能依赖 `debug_assert!`。

## 2. 诊断信息

说明失败的操作、对象、阶段和必要上下文，同时避免输出凭据、密钥、用户内容或无界数据。底层返回结构化错误，上层只在增加新的决策语境时补充路径、provider、模型、项目或阶段信息。

不要在多个抽象层重复记录同一根因。重试、流式事件和轮询日志必须有界。运行器要让内部失败传播到最外层退出状态；只有零退出码而没有目标行为的可观察后置条件，不算成功证据。

## 3. 测试与回归

把测试放在最接近被保护不变量、又能观察真实行为的层级。纯规则使用单元或组件测试；跨 crate 协议使用集成或契约测试；Rust/FRB/Dart/GUI 的完整交互使用项目规定的 GUI integration、Web integration 或 Driver 入口。

修复缺陷时，让回归测试在错误实现上稳定失败，再让同一测试在修复后通过。回归直接触发根因，不通过概率复现、延长超时、放宽断言或删减用例取得绿色。

至少按实际风险覆盖成功、错误、边界、资源释放和重复调用。状态机覆盖可达转换和重要非法转换；解析器覆盖截断、溢出、未知字段和不可信长度；所有权改动覆盖部分构造、提前返回与析构。

测试要编译真实实现并观察行为。只有被测对象本身是源码文本、生成模板或静态契约时，才使用文本搜索作为主要断言，并说明理由。确认测试能被仓库入口发现、执行，并在回归时使最外层任务失败。

## 4. 验证选择

先运行受影响 crate 或用例的定向检查，失败时保留原始错误。交付前依据根目录 `AGENTS.md` 选择完整门禁；Rust 改动的标准入口包括：

```text
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

GUI、Dart、生成文件和 live provider 采用 `AGENTS.md` 指定的独立入口与 opt-in 规则。不要默认启用依赖外部服务的 feature，也不要用原生 Flutter/Dart 命令绕过仓库包装入口。
